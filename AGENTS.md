# Правила для ИИ-агентов (Codex, Claude Code и др.)

Ты помогаешь одному человеку из команды из трёх на **41 PlayLab Game Jam '26**. Делаем оригинальную игру на Unity **6000.3.29f1** (Built-in RP). Роли и план — `README.md`, подключение — `docs/ONBOARDING.md`.

## Кто ты в этой сессии

1. Прочитай файл `.agent-role` в корне репозитория (он локальный, не в git). Первая строка — роль: `design-ui`, `gameplay` или `systems`; вторая — имя человека.
2. Прочитай инструкцию своей роли `docs/roles/<роль>.md` и работай по ней.
3. Файла `.agent-role` нет — значит, подключение не пройдено: спроси человека его роль и выполни `docs/ONBOARDING.md`.

## Язык

- С человеком говори **по-русски**.
- **Игра — полностью на английском.** Всё, что видит игрок: меню, кнопки, HUD, обучение, подсказки, сюжет, диалоги, названия уровней и предметов, экраны победы и поражения, титры, название игры.
- Внутри `Assets/` всё на английском: имена файлов, объектов, классов, переменных, комментарии в коде. Тогда проверка ниже ловит только настоящие ошибки.
- Перед каждым коммитом проверь, что в добавленном нет кириллицы и турецких букв:
  ```
  git diff --cached -U0 -- Assets | grep '^+' | grep -nE '[А-Яа-яЁёĞğÜüŞşİıÖöÇç]'
  ```
  Пусто — хорошо. Что-то нашлось — переведи на английский.

## Условия джема

- Тема — **Kontrol etmek** («контролировать», «управлять», «проверять»). Контроль должен быть заметен в самом действии игрока, а не только в сюжете.
- **41 час** от объявления темы, игра с нуля, одна игра от команды.
- **Сдача через itch.io до 12:00, 29 ноября 2026, по турецкому времени (UTC+3).** Обязательна рабочая **сборка под Windows**. Браузерная версия — по желанию.
- ИИ и ассеты из маркетплейсов разрешены. Всё взятое сразу записывай в `CREDITS.md` (в раздел своей роли) — из него перед сдачей делаются титры игры.
- Показ жюри — **5 минут**. Нужно короткое обучение внутри игры.

## Как работать

1. Сначала **одна короткая сессия целиком**: игрок заходит, понимает управление, совершает действие, получает результат. Временные ассеты — где они ускоряют проверку. Историю, визуал, звук и уровни развивай вокруг того, что уже работает.
2. **Сборку под Windows проверяем рано** и потом регулярно (этим занимаются Системы). Не проверенный запуск — сообщи человеку, что он не проверен.
3. Проверяй управление, обучение и возможность начать заново.
4. После заметного этапа коротко скажи человеку, что уже можно запустить и проверить.
5. Мало времени — предложи, что вырезать, чтобы сохранить законченную игровую сессию и рабочую сборку.
6. **Публикуешь на itch.io и отправляешь игру только по явному указанию человека.**
7. Простота важнее архитектуры: это джем, а не продукт.

## Синхронизация с командой (обязательно)

Все работают в одной ветке **`main`**. Каждый трогает только свою зону, поэтому конфликтов почти нет — если синхронизироваться часто.

**В начале каждой задачи:**
1. Попроси человека сохранить всё в Unity (Cmd/Ctrl+S).
2. `git fetch`, затем `git log --oneline HEAD..@{u}` — покажи человеку, что пришло от команды (кто и что).
3. `git pull` (в репозитории включены `pull.rebase` и `rebase.autoStash`, свои незакоммиченные правки не потеряются).
4. Попроси человека переключиться в Unity и дождаться импорта; консоль без красных ошибок.

**Когда кусок работы готов — коммить и пушь сразу** (обычно раз в 30–60 минут, не копи):
1. Unity: консоль без красных ошибок, Play запускается.
2. `git status` — коммить **только файлы своей зоны** вместе с их `.meta`. Изменения в чужих папках, `ProjectSettings/`, `Packages/` — не коммить, скажи человеку (обычно это Unity сам что-то переписал или нужна просьба к Системам).
3. Проверка английского (см. выше).
4. `git add <свои пути>` → `git commit -m "<роль>: что сделано"` → `git pull` → `git push`.
5. Одной строкой скажи человеку, что ушло, чтобы он написал в чат команды «запушил: …» — напарники сделают `git pull`.

**Если что-то пошло не так:**
- `git push` отклонён (кто-то запушил раньше) → `git pull`, потом снова `git push`.
- Конфликт при `git pull` → остановись и покажи человеку файлы. Чужие файлы не решай сам — спроси владельца. Сцены и префабы Unity руками не склеивай: берётся целиком одна версия.
- В `main` ошибка компиляции → кто сломал, чинит сразу; не успевает — `git revert <коммит>`.

## Запрещено

- `git push --force`, `git reset --hard` по запушенным коммитам, `git clean -x`/`-X`, переписывание истории `main`.
- Коммитить `Library/`, `Temp/`, `Logs/`, `UserSettings/`, сборки, `.agent-role`, файлы больше 50 МБ (у GitHub лимит 100 МБ; исходники `.psd`, `.aep`, `.blend`, исходные `.wav` — на общий Drive, в Unity — только экспорт).
- Коммитить изменения `ProjectSettings/ProjectVersion.txt` — это значит, что проект открыт не той версией Unity: остановись и скажи человеку.
- Править чужие зоны без просьбы владельца. `ProjectSettings/`, `Packages/` и `Scenes/Main.unity` — зона Систем.

## Unity

- Не создавай, не переименовывай, не перемещай и не удаляй ассеты в обход Unity: у каждого ассета есть `.meta` с GUID, на нём держатся все ссылки. Новые `.cs` можно создавать файлом — Unity сделает `.meta` сам; потом проверь консоль.
- `.unity` и `.prefab` не правь как текст, если можно через редактор (MCP for Unity) или скриптом.
- Одну сцену или префаб двое одновременно не правят. Своя песочница `Scenes/Sandbox/<Name>.unity` — для любых проб.
- Связь между ролями — через публичные методы и C#-события (`GameManager`, `AudioManager`, события игрока), а не через поиск объектов по имени.
- Ввод — старый Input Manager (`UnityEngine.Input`), UI — uGUI + TextMeshPro (`com.unity.ugui`).
